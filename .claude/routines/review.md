# レビューの手順書

PR が Ready for review になったときに起動します。実装した役とは別のセッションで、PR を独立にレビューします。コードは直しません。

## 1. 起動してよいかを確かめる

次のどれかに当たれば、何もせずに終える。

- PR が閉じている、draft である。
- head のブランチが `claude/` で始まらない。
- PR に `needs-human` が付いている。
- PR の最新のコミットに対するレビュー（`<!-- factory:review ... commit=<最新のコミット> -->`）が、もうある（同じ版を二度レビューしない）。
- 最新の `verdict=ok` のレビューの後に入ったコミットが、すべて「取り込みだけのコミット」（`README.md` の「どの役にも共通の決まり」）である（中身は変わっていない）。

### 軽い再レビュー

前回のレビューが `verdict=ok` で、その後に PR に入ったコミットが「`main` の取り込み（マージのコミット）」と、その衝突の解消だけなら、2 段の確かめはせず、次だけを行う。

- 衝突を解消した箇所（マージのコミットで、`main` の側とも PR の側とも違う行）を読み、両方の変更の意図が残っているかを見る。
- `npm run typecheck`・`npm test`・`npm run build` が通るかを見る。

問題が無ければ verdict=ok にする（コメントに「軽い再レビュー」と書く）。少しでも PR の側の変更（機能の変更）が入っていれば、通常のレビューをする。

## 2. 確かめる

PR が `Closes #<番号>` で参照する Issue を読み、次の 2 段を順に行う。2 段を混ぜない。`Closes` の Issue が無い PR（手順書や設定だけの変更など）は、受入条件の代わりに PR 本文の「変更内容」と照合する。

1. **要件の照合**: Issue の受入条件を 1 つずつ取り上げ、満たしているかを、コードとテストを読んで判定する。判定ごとに根拠（ファイルと行、テストの名前）を書く。受入条件に書かれていないが、同じ画面・API の既存の振る舞い（ログインの確認、入力の検証、エラーの形）とそろっているかも見る。
2. **動かして確かめる**: PR のブランチで `npm run build` と `npm start` を実行し、変更した画面と API を実際に開く（`curl` か Playwright）。ログインが要るものは、初期ユーザー（`AGENTS.md` を参照）でログインしてから確かめる。開いた URL・状態コード・エラーの有無を結果として書く。

あわせて、PR が `main` と衝突していないか（`mergeable`）を見る。衝突していれば、それを「必須」の指摘にする。

PR が高リスクの変更（DB のスキーマ `src/lib/db/migrations.ts`／ログイン・セッション・権限の判定 `src/lib/auth.ts`・`src/lib/session.ts`・`src/lib/api.ts` の `requireApiUser` など／他人のデータを見せる・変える範囲が変わる変更）に当たれば、PR に `risk:high` を付け、レビューのコメントにどれに当たるかを書く。verdict には影響させない。

## 3. 結果を書く

PR にレビューのコメントを 1 つ書く（`pull_request_review_write` の `COMMENT`。Approve はしない）。先頭は次の形にする。

```
<!-- factory:review verdict=<ok|changes> round=<この PR で何回目のレビューか> commit=<レビューしたコミットの SHA> -->
```

- 直すべき指摘には、それぞれ「必須」を付け、どの受入条件・どの確かめた結果に反するかを書く。好みの問題は「任意」にし、verdict には数えない。
- 「必須」が 1 つでもあれば verdict=changes にし、PR を draft に戻す（これが修正の起動の合図）。
- 無ければ verdict=ok にし、Ready のままにする。人がマージするので、それ以上は何もしない。
