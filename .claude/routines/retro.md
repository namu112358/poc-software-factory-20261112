# 振り返りの手順書

1 日 1 回起動します（人が「今すぐ実行」してもよい）。マージされた PR のレビューの指摘から、ほかの機能でもくり返しそうな決まりを拾い、`AGENTS.md` の「このプロジェクトの罠」に足す案を、人が判断できる PR にします（開発標準 §2.10 の改善ループ）。コードは書きません。

## 1. 指摘を集める

前回の振り返り（Issue「Factory の運用の記録」にある `<!-- factory:retro until=<日時> -->` のコメント）より後にマージされた `claude/` の PR を集める。前回が無ければ、すべてのマージ済みの PR を対象にする。

それぞれの PR のレビュー（`<!-- factory:review verdict=changes ... -->`）の「必須」の指摘と、修正の役のコメント（`<!-- factory:fix -->`）を読み、指摘ごとに「何がまずかったか」を 1 行にまとめる。`main` との衝突だけの指摘は除く。

「任意」の指摘も、同じように 1 行にまとめる。任意の指摘は、前回までの振り返りの期間も含めて 3 つ以上の PR でくり返したものだけを、次の「2.」の候補にする（任意の指摘は 1 回では直されないので、くり返しの数で選ぶ）。前回までの数は、これまでの振り返りの記録（「4.」）に残した任意の指摘の一覧から数える。

### 流れの止まり・遅れも集める

同じ期間について、次のものも集める（レビューの指摘には出ない、流れの問題を拾うため）。対象は、マージされた `claude/` の PR に加えて、同じ期間にマージされずに閉じた `claude/` の PR と、それらの Issue。マージされずに閉じた PR は、閉じたときのコメントに止まりの原因が書かれていることが多い（2026-11-12 の #58 では、「ブランチが古い版から作られていた」という原因が、そこにしか無かった）。

- `status:in-progress` が付いてから PR が Ready になるまでに 10 分以上かかった Issue と、その間に何が起きたか（衝突・CI の待ち など）。あわせて、`status:ready` が付いてから `status:in-progress` が付くまでの待ち（空き待ち・同じファイル待ち・依存先待ち）
- 実装・修正の役が、待ちきれずに終えたり、`status:needs-human`・`status:blocked-question` で止まったりした回と、その理由。理由は役のコメントだけでなく、その後に人や別の役が書いたコメントと、PR を閉じた理由まで読む
- 衝突で draft に戻された回数（PR ごと）と、キューで待った時間
- レビューで `verdict=ok` になってからマージされるまでに 10 分以上かかった PR と、その間に何が起きたか（Mergify のキューから外れた・衝突・人の判断の待ち など）

マージされずに閉じた PR のうち、閉じたときのコメントに、止まりではなく意図して閉じた理由（比べるための試行・重複・方針の変更など）が書かれているものは、止まりに数えない。

時刻は次の道具で取る（GitHub MCP の `issue_read` では、ラベルが付いた時刻が取れない）。

- ラベルが付いた・外れた時刻: REST の `GET /repos/{owner}/{repo}/issues/{number}/events`（`labeled`・`unlabeled`）
- PR が Ready になった・draft に戻った時刻: REST の `GET /repos/{owner}/{repo}/issues/{number}/timeline`（`ready_for_review`・`convert_to_draft`）
- Mergify のキューの出入り: PR の Mergify のコメント（外れた理由は `dequeue_reason`）
- CI が動いたか: REST の `GET /repos/{owner}/{repo}/commits/{sha}/check-runs` と、PR の `mergeable`（`main` と衝突している PR では、CI が動かない）

ラベルの名前は 2026-11-12 に、用途のグループを接頭に付けた名前に変えた。それより前の記録（コメント・イベント）には旧名が残っていることがあるので、旧名も同じラベルとして数える: `ready` → `status:ready`、`in-progress` → `status:in-progress`、`in-progress:hard` → `status:in-progress-hard`、`blocked:question` → `status:blocked-question`、`needs-human` → `status:needs-human`、`epic` → `kind:epic`、`kaizen` → `kind:kaizen`、`merge` → `merge:requested`、`enhancement` → `type:feat`、`bug` → `type:fix`。

## 2. くり返しそうなものを選ぶ

次の 2 つをどちらも満たすものだけを選ぶ。満たすか迷うものは選ばない。

- その機能だけの話ではなく、ほかの機能を作るときにも同じ間違いが起きうる（例: 「一覧で複数の値を区切らずに並べた」は、ほかの一覧でも起きうる。「延長申請の理由の上限を間違えた」は、その機能だけの話）。
- `AGENTS.md`（コーディング規約・罠）に、まだ同じ内容が無い。

「罠」に足す候補は、さらに次の 2 つを確かめ、どちらも当てはまるものだけを選ぶ。確かめた結果は、PR の本文に書く。

- コードや一般の作法からは推し量れない、このプロジェクトだけの決め事である（例: 「新しい画面はヘッダーにリンクを足す」は、推し量れない。「更新したら updated_at も変える」「文字数はコードポイントで数える」は、既存のコードや一般の作法から推し量れる）。2026-11-12 の試行（Epic #121）では、推し量れる落とし穴は、決まりが無くても実装の役が 6 件中 6 件で避けた。推し量れない決め事は、決まりを足す前は 2 件中 0 件、足した後は 2 件中 2 件で守られた。
- 決まりの無い状態で、今の実装の役が実際に誤る。最後に誤った PR が、直近の 2 回の振り返りの期間の中にあるかで判断する。無ければ、同じ型の小さな課題を、サブエージェント（実装の役と同じモデル）に決まりを見せずに 1 回解かせ、誤るかを見る。

流れの止まり・遅れは、原因が手順書（`.claude/routines/`）にあり、手順書を直せばくり返さないものだけを選ぶ（1 回の振り返りで 2 件まで）。原因が手順書の外（Routine の設定・`.mergify.yml`・Ruleset）にあるものは選ばず、「4.」の記録にだけ書く。

選ぶ前に、その原因がもう直っていないかを確かめる。出来事の時刻より後に `.claude/routines/` を変えたコミット（`git log --since=<出来事の時刻> -- .claude/routines/`）と、出来事に付いたコメント（「直した」「指示文を変えた」など）を読む。直っていれば選ばず、「4.」の記録に「直し済み（#番号）」と書く。

## 3. 案を PR にする

選んだものがあれば、`claude/retro-<日付>` のブランチで、`AGENTS.md` の「このプロジェクトの罠」に 1 件ずつ足し、draft の PR を出す。

- 書き方は `AGENTS.md` の「罠」の書き方に合わせる（言い切りの規約の行と、その下の「理由」の行）。理由には、きっかけになった PR の番号を書く。
- 1 回の振り返りで足すのは 3 件まで。多ければ、くり返しそうな順に選ぶ。
- PR は draft のままにする（Ready にしない。レビューの役ではなく、人が判断する）。

流れの止まり・遅れの直しは、別の draft の PR（`claude/retro-flow-<日付>`）で、`.claude/routines/` の手順書を直す案として出す。何が起きたか（Issue・PR の番号と時刻）と、直した後にどう変わるかを本文に書く。

選んだものが無ければ、PR は出さない。

## 4. 記録する

Issue「Factory の運用の記録」に、`<!-- factory:retro until=<今回の対象の最後のマージの日時> -->` を先頭に付けて、集めた指摘の数・選んだもの（と PR の番号）・選ばなかった主なものとその理由・罠の決まりごとの効き目の数を、短く書く。あわせて、任意の指摘を「何がまずかったか」の 1 行と PR の番号で残す（次回の振り返りが、くり返しの数を数えるため）。

記録には、「罠」に足した決まりの効き目の数を含める。罠の行のうち、理由に PR の番号が書かれているもの（振り返りで足したもの）について、今回の期間の PR で次の 2 つを数える。

- 同じ誤りが、レビューの指摘（必須・任意）に出た PR の数
- 実装の役が、PR 本文の「注意事項・残課題」で、その決まりを当てはめたと書いた PR の数

3 回の振り返りで続けて同じ誤りが出ている決まりは、より手前の段（型・Lint・単体テスト）に移す案を、この記録に文章で書く（どの段に、何を確かめるものを足すか）。振り返りの役はコードを書かないので、型・テスト・Lint の設定は変えず、PR にも入れない（移すかは人が決め、移すなら Issue にする）。3 回の振り返りで続けて、誤りも当てはめも 0 件の決まりは、外す候補として記録に書く（外すかは人が決める）。
