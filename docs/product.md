# このアプリで良くしたいこと

Issue を作るときの拠り所です。Issue は、下の「良くしたいこと」のどれかにつなげ、本文の冒頭に「どの困りごとを、どう良くするか」を 1 行書きます。

## だれが何のために使うか

数人のチーム（今は佐藤・鈴木・田中）が、日々の作業をタスクとして持ち、だれが何をいつまでにやるかを共有するためのアプリです。

- **メンバー**: 自分の担当のタスクを進め、間に合わなければ期限の延長を申請する。
- **取りまとめる人**: チーム全体の進み具合を見て、担当を割り振り直し、延長の申請を承認する。
- 社内の連携スクリプトが API でタスクを読み書きすることもある。

## 次の 1 か月で良くしたいこと

1. **期限に遅れそうなタスクに、早く気づいて手を打てる**
   期限切れや期限間近のタスク、承認を待っている延長の申請が、探さなくても目に入る。
2. **担当の割り振りや引き継ぎを、安全に、手早くできる**
   異動や休みのときに、複数のタスクの担当をまとめて替えられ、だれがいつ替えたかを後から確かめられる。
3. **目当てのタスクに、すぐたどり着ける**
   タスクが増えても、キーワード・担当者・タグ・期限で絞り込み、並べ替えて、探す時間を減らす。表記の揺れも減らす。
4. **同時に触っても、間違えて操作しても、データを失わない**
   2 人が同じタスクを直しても上書きし合わない。消す前に確かめ、消さずに隠す手段（アーカイブ）もある。
5. **自分のアカウントを、自分で守れる**
   身に覚えのないログインに気づける。（パスワードの変更と、ほかの端末のログインを切る操作は、すでにできる）

次のことは、使って確かめて、困りごとにしなかった。

- だれがいつ担当を替えたかは、タスクの詳細の「担当者の履歴」に残る。
- 新しく担当になったタスクは、次のログインのときに知らされる。
- ほかの端末のログインは「ログイン中の端末」に出て、その端末だけを切れる。

- ログインとフォームの誤りは、読み上げられる。削除の前の確認は、キーボードで答えられる。

- 「すべての端末からログアウト」で、すべての端末のログインが切れる。

次は、2026-11-13 03:38 に、社内の連携スクリプトが API でタスクを書き込む立場で使って見つけたこと（3 回目の連携スクリプトの回は読み取りが中心だった）。3 つを Issue にした（Epic #511）。

- 1・4 について（#512）: タスクの期限に、存在しない日付（2026-02-30 など）が保存される。延長の申請は同じ日付を断るので、API ごとに扱いが違う。
- 連携スクリプトについて（#513）: ログインの API に JSON の Content-Type を付けずに送ると、500 で本文が空になる。何が悪いのか分からない。
- 4 について（#514）: 何も変えない更新（`PATCH {}`）でも更新日時が進む。同時の更新を確かめているほかの人の保存が、変更が無いのに断られる。

次のことは、今の API の振る舞いを変えると、すでにある連携スクリプトを壊すおそれがある。そのため Issue にせず、人の判断に残した。

- 更新で `expectedUpdatedAt` を付けないと、ほかの人の更新を黙って上書きする。
- 知らない項目（項目名のタイプミスを含む）は、黙って無視される。（後に取りまとめ役が仕様を決め（Epic #525）、#527 で 400 で知らせるようにした）
- 同じ内容の作成を 2 回送ると、2 つできる。（後に取りまとめ役が仕様を決め（Epic #525）、#528 で任意の Idempotency-Key で防げるようにした）

次のことは、使って確かめて、困りごとにしなかった。

- ほかの人の担当のタスクも編集できる。チームで使う作りとして意図どおりとみた。削除と元に戻すは担当者だけ。
- まとめての変更は、存在しない ID や削除済みの ID が 1 つでも混ざると、全部を変えずに断る。断った ID は応答に並ぶ。
- 延長の申請の承認は、取りまとめる人だけができ、自分の申請は判断できない。

## Issue にしないもの

- 良くしたいことのどれにもつながらない変更。
- 使う人にとって意味のある変化にならない、小さな飾りだけの変更（例: 件数を 1 つ表示するだけ）。必要なら、意味のある変更の一部として扱う。
