# [SF-D][Epic] 取りまとめる人が、メンバーの出入りをアプリの中で扱えるようにする（#521）の結果

連続運転 D（2026-11-13、計画は #122）のうち、チームにメンバーが加わる・抜けるときの取りまとめる人の立場で使って見つけた困りごとを直した Epic の結果です。使う人の立場で動かす回の 10 回目（04:05、main b3fc1d6）で見つけ、11 回目（05:05、メンバーが辞めるとき）で、直した後のつなぎ目をもう一度見ました。

## 確かめたいこと

- メンバーの出入りを扱う手段（加える・ログインを止める・役割を替える）が、取りまとめ役の決めた仕様どおりに動くか。仕様は取りまとめ役が PoC のアプリの仕様として決めた（04:05。ユーザーに知らせ、覆されたら直す）。
- 認証と権限に触れる 4 件を、`risk:high` の流れ（レビューの後に D が差分を読む）で、止まらずに流せるか。

## 見つけ方

10 回目は、main を起動し、取りまとめる人（田中）とメンバー（佐藤・鈴木）の 3 つのブラウザで、メンバーが加わる・抜ける場面を操作した。操作と記録はサブエージェント（sonnet）に任せ、困りごとの見立ては D がした。次の 3 つが、アプリにまったく無かった。

- 新しいメンバーを加える画面も API も無い（利用者は初期データの 3 人だけ）。
- 抜けるメンバーのログインを止める手段が無い。担当をすべて替えたあとも、鈴木はログインでき、ほかの人のタスクを変えられ、新しい担当にもなれた。
- 取りまとめる人の役割を替える手段が無く、役割は画面にも `GET /api/me` にも出ない。

11 回目は、#522（停止）のマージ後に、辞めるメンバーの持ち物（担当のタスク・延長の申請・休み・コメント・CSV）が停止の前後でどう見えるかを見た。停止して残ったタスクに取りまとめる人が気づけない、という困りごとを見つけ、#538 にした。

確かめ直しの中身（操作はサブエージェント（sonnet）に任せ、判定は D がした）:

1. #522（停止・再開。11 回目の探索で、マージ後の main を使って確かめた）
   - 田中がメンバーの画面で鈴木を停止すると、確認が出て、鈴木の開いていたブラウザはログイン画面に戻った（API は 401）。鈴木はログインできない（応答は、パスワードの誤りと同じ）。
   - 鈴木は担当の選択肢から外れ、作成・更新で鈴木を担当にすると 400。絞り込みでは「鈴木（停止中）」として残り、引き継ぐタスクを探せた。
   - 自分自身の停止は 400、いない人は 404。再開すると、またログインできた（停止の前のセッションは戻らない）。
2. #523（アカウントの作成）
   - 作れるのは取りまとめる人だけ（佐藤は 403、画面に操作も出ない）。ID・名前の誤り・知らない項目は 400、すでにある ID（停止中を含む）は 409。
   - 仮のパスワード（20 文字）は、作った直後に一度だけ表示され、再読み込みで消えた。
   - 仮のパスワードでログインすると、パスワード変更の画面に移り、変えるまでほかの画面は移され、API は 403。変えると、ふつうに使え、担当の選択肢に出た。古い仮のパスワードではログインできない。
3. #524（役割の付け替え）
   - 役割を替えられるのは取りまとめる人だけ（佐藤は 403、画面にボタンも出ない）。不正な役割・知らない項目は 400、いない人は 404、同じ役割への変更は何も変えずに 200。
   - 唯一の取りまとめる人（田中）が自分をメンバーに戻すと、確認のあと 409（「取りまとめる人が 1 人もいなくなるため、メンバーに戻せません。…」）で、役割は変わらない。停止中の人を取りまとめる人にすると 409。
   - 佐藤を取りまとめる人にしてから田中が自分を戻すと 200。戻した田中は、役割の変更も延長の承認も 403 になり、佐藤は延長を承認できた。
   - 役割は、メンバーの一覧の「役割」の列、ヘッダー（「役割: 取りまとめる人」）、`GET /api/me`・`GET /api/users` に出た。
4. #538（停止した人に残ったタスク）
   - 停止した直後に「鈴木 さんの未完了のタスクが 4 件残っています。担当を替えてください。」と、絞り込んだ一覧へのリンクが出た。0 件なら残っていないと出た。
   - 田中の「あなたの対応が必要なもの」に、停止した人ごとの件数とリンクが出て、担当を替えて 0 件になると消えた。佐藤には出ない。停止した人が 2 人なら 2 人分が出た。
   - タスク一覧と期限切れの一覧で、担当者に「（停止中）」が付き、再開で消えた。完了・削除したタスクは件数に入らない。

時刻はすべて UTC。ready・着手の時刻は GitHub のラベルのイベント、マージの時刻は PR のマージの時刻による。

## 分かったこと

- 「アプリにまったく無い」種類の困りごとは、仕様（だれが・何を・どこまで）が決まっていないと Issue にできず、人の判断待ちになっていた。取りまとめ役が仕様を決めると、2 時間弱で 4 件ともマージまで進んだ（04:05 に決めて、05:58 に最後のマージ）。
- 停止を足した後のつなぎ目（停止した人に残ったタスク）は、停止の Issue の受入条件には無く、マージ後にもう一度使って初めて見えた（台帳 E15 と同じ形）。新しい状態（停止中）を足したら、その状態のものがほかの画面でどう見えるかを、続けて 1 回確かめると拾える。
- 同じファイル（利用者・メンバーの処理）を変える Issue が続いたため、割り当ての待ちで 1 件ずつ流れた。#538 と #524 は、割り当てがほぼ同時に着手させ、先に着手した #538 が説明なしに待ちに戻されたのに、実装は続いた（台帳 E33）。今回は #538 が先にマージされ、衝突も二重の着手も起きなかった。

## 対象外にしたこと（困りごとにしなかったこと）

- 停止中の人のログインの応答が、パスワードの誤りと同じ（ID の有無や停止を外に漏らさない作り）。
- 仮のパスワードの間も、ヘッダーにすべての画面へのリンクが出る（押すと変更画面に戻る）。パスワードを変えたあと、自動ではタスク一覧に移らない（「タスク一覧へ進む」のリンクで進む）。
- 停止した人のコメント・担当の履歴・休みの記録は、名前のまま残る（過去の記録を残す仕様どおり）。
