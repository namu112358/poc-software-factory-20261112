# 待ちが集まるファイルを分けると、並列に作れる数が増えるか（Epic #262）

2026-11-12 の PoC の結果。経過と生の数字は Epic #262 のコメントにある。

## 結論

- タスクの処理を 1 つのファイル（`src/lib/tasks.ts`）から機能ごとの 5 つのファイルに分けても、互いに重ならずに同時に着手できる数は **4 件 → 4 件で変わらなかった**。待ちが集まる場所は、画面のファイル（`src/app/tasks/page.tsx`・`src/app/tasks/[id]/page.tsx`）に移った。
- 分けた直後に実際に着手できたのは 1 件だけだった。キューに残る記録（待ち先・変えるファイルの見積もり）が分ける前のままで、待つ理由が無くなっても解けなかった。
- 並列度を決めていたのは、ファイルの分け方よりもキューの判定だった。待ちの数珠つなぎを 1 段にし、待つ理由が無くなった待ちを解く直し（#274）の後、作業中は 1 件から 3 件に増えた（13:56 UTC）。

## 標準の案に入れるもの

- AI に並列で作らせるとき、触る場所が集まるファイルを分けるのは、集まっている場所（画面も含む）をまとめて見てから。1 つ分けても、次の場所に移るだけのことがある。
- 同じファイルの待ちは、動いている作業だけを待つ。キューの中の待ちは 1 段まで。待つ理由は、待ち先の今の変更ファイルで判定し直す（#274）。
- 予約の順番より優先したい作業（分割など）は、人が依存（blocked by）で表す。

## 残ったこと

- キューにいる Issue の見積もり（`files=`）は、ファイルの構成が変わっても書き直されない。構成の大きな変更はまれなので、仕組みは足さず、必要なら人が `status:ready` を付け直して見積もりをやり直させる（取りまとめ役の判断）。
- 1〜2 時間の作業中の件数の比較は、台帳 #123 の #275 の行（D の連続運転）で判定する。
