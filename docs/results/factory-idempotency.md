# 重複着手と冪等性（Factory の運用、2026-11-12〜13）

GitHub のイベントで動く Routine は、同じ仕事を 2 つ以上の役が同時に始めることがありました。GitHub の Issue・PR のラベルやコメントには、ほかの役を止める鍵（排他）がありません。この文書は、重複着手の形と対策、その効き目と、残る弱点をまとめます。課題ごとの判定の正本は台帳 #123 です。

## 起きた形

| # | 形 | 例 | 原因 |
|---|---|---|---|

| 2 | 割り当ての役が 2 つ同時に動き、同じ Issue・PR を二重に処理する | #220（16:48 の #259・#312、01:02 の #468） | PR が続けて閉じる・承認が重なるなど、きっかけのイベントが数秒の間に複数来る |
| 3 | 承認（`ready`）を外した直後に、着手の合図が付く | #322（#310） | 割り当てが、読み込んだ時点のラベルで判断し、付ける直前に読み直していなかった |

## 対策と効き目

| 対策 | 形 | 直した PR | 効き目（台帳 #123） |
|---|---|---|---|

## 原則

1. 状態は GitHub だけに持ち、役は起動のイベントではなく、今の状態を読み直して判断する。
2. 開始の合図を付ける役を 1 つに絞る。
3. 動く前と動いた後に読み直し、先に着手したほうが勝つ。
4. ブランチ名を Issue ごとに 1 つに決め、残ったものは引き継ぐ。
5. ラベル・コメントには排他の鍵が無いので、数秒のすき間の重なりは残る。重なっても害が小さい作り（後から気づいた側が何もせずに終える・同じ操作をくり返しても結果が同じ）で受ける。

## 残る弱点

- 数秒のすき間の重なりは防げない。2 つの役が同時に「まだ誰も着手していない」と読み、同時に書き込むと、どちらも気づかない（#259・#312・#468 の二重の割り当て、#429 の 3 重の着手）。
- 重なったときの無駄（セッションの起動・計画の書き込み・起動の回数の予算）は残る。#429 では、3 つのセッションが計画まで書いた。
- 次の仮説（台帳 #123 の E25。ユーザーの了承済み、これから直す）: 実装の役が最初に GitHub 上で `claude/issue-<番号>` のブランチを作り、すでにあれば何もせずに終える。同じ名前のブランチの作成は失敗するので、これが排他の鍵になる。
