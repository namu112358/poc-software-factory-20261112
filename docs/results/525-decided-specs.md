- ログインのロックの方針（Epic #477 で対象外にした）
- API の振る舞い 3 つ（Epic #511 で対象外にした）

- 今の画面と連携スクリプトの使い方を壊さないか（どれも既存の振る舞いを変えるので `risk:high`）。
- `risk:high` の PR を、人（D）が差分を読んでからマージに回す流れで、止まらずに回るか。

3 件とも、マイグレーションか同じ API のファイルを変えるので、割り当てが同じファイルの待ちで 1 件ずつ流した（#527 → #526 → #523（Epic #521）→ #528）。待ちの解除は、どれも人の操作なしで、前の PR のマージから 1〜2 分で着手した。

確かめ直しの中身（操作はサブエージェント（sonnet）に任せ、判定は D がした）:

1. #527（知らない項目は 400）
   - 作成・更新・まとめての変更（本文と `changes` の中）・まとめての完了・取り消し・コメント・タグ・タグの名前の変更・延長の申請・休み・パスワードの 17 通りで、知らない項目は 400（`details` に項目名と、受け付ける項目）。何も変わらなかった。
   - サーバーが付ける項目（`id`・`createdAt`・`updatedAt`・`completedAt`）は「サーバーが付ける項目のため、送れません」で 400。
   - 画面の 10 の操作は、400 以上の応答なしで通った。
   - 範囲外: 本文を使わない複製の API と、画面のフォームから送るログインは、知らない項目を無視する（困りごとにしない）。
2. #526（ロックを接続元ごとに）
   - 接続元 A から 5 回誤ると、A からは正しいパスワードでも 429、接続元 B からは 200。存在しない ID も同じ並び・同じ文言。
   - 8 つの接続元から計 30 回誤ると、新しい接続元からも 429（アカウント全体のロック）。
   - フォーム送信も同じ。B からログインした画面に、ロックされたことの知らせが出た。パスワード変更は今までどおり。
   - 残るリスク（PR #537 に明記）: 接続元は `X-Forwarded-For` のいちばん右の値で見分けるので、プロキシを置かずに公開すると送る側が偽れる。偽っても全体の 30 回で止まる。
3. #528（Idempotency-Key）
   - 同じキー・同じ本文の送り直しは、作成もコメントも 2 回とも 201 で同じものを返し、1 つしかできなかった。項目の順だけ違う本文も同じ扱い。
   - 同じキーを 5 本同時に送っても、できたのは 1 つで、5 本とも同じ ID を返した。
   - 同じキーで本文が違えば 409 で何も作らない。コメントは対象のタスクも照合するので、別のタスクに同じキーで送ると 409。
   - キーなしは今までどおり毎回作る。ほかの利用者が同じキーを使っても別のものとして作る。
   - 不正なキー（空・空白入り・256 文字・ASCII 以外）は 400 で何も作らない。255 文字は通る。
   - 入力の誤りで断った送信はキーに残らず、直して同じキーで送ると作られた。
   - 画面からの作成・コメントは、400 以上の応答なしで通った。
   - 24 時間の期限切れは、実際のサーバーでは確かめていない（DB がメモリ上で、記録の時刻を外から変えられないため）。単体テスト（24 時間の 1 秒前は 1 回目を返し、ちょうど 24 時間で新しく作る）で確かめた。

時刻はすべて UTC。ready・着手の時刻は GitHub のラベルのイベント、マージの時刻は PR のマージの時刻による。

## 分かったこと

- 人の判断待ちにしていた 2 つの点は、取りまとめ役が仕様を決めると、1 時間 40 分で 3 件ともマージまで進んだ（04:05 に決めて、05:46 に最後のマージ）。判断待ちのまま置くより、決めて直し、覆されたら戻すほうが速い（ユーザーの方針「課金や危険なこと以外は、人の承認で止めない」）。
- `risk:high` の 3 件は、どれもレビューの 1 回目で ok になり、D が差分を読んでも直しを求める点は無かった。D が読む時間（merge-check の ok から `merge:requested` まで）は 1〜2 分で、流れを止めなかった。
- 互換性への備え: 「今の画面が送る本文がそのまま通る」ことを受入条件に入れたので、実装の PR のテストが、画面の送る本文を 1 つずつ確かめていた。マージ後の確かめでも、画面の操作の壊れは 0 件だった。
- 同じファイルの待ちで 1 件ずつ流したため、ready から マージまでは 39〜55 分かかった（作業そのものは 15〜20 分）。マイグレーションを足す Issue が続くと、待ちが長くなる。

## 対象外にしたこと

- ロックの方針の残り（プロキシの段数の設定、IPv6 を /64 でまとめる）: 本番の置き方が決まってから。
- `docs/product.md` の「人の判断に残した」の行は、過去の記録として残し、決まって直したことを書き足した（この PR）。
