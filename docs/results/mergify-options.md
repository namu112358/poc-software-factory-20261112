# Mergify をもっと活かす案と、測り方（2026-11-13）

Mergify のマージキューの設定で、PR がマージされるまでの待ちと、やり直しの手間を減らせるかを、2 日分の記録と Mergify の公式の文書から検討した。結論と、試す順番、測り方をまとめる。`.mergify.yml` を変える PR は、人がキューを通さずにマージする（#145）ので、この文書は案と計画までにとどめる。

## 結論

- **今のキューは、ふだんは詰まっていない。** キューに入ってからマージまで中央値 2.2 分、キューの中の CI は 1 回あたり中央値 45 秒。キューに入った時点で先にいた PR は平均 1.04 本（半分以上は 0 本）。混んだのは 11-12 の午後の一時だけ（同時に最大 12 本、待ちは最大 21 分）。
- **やり直しの手間の多くは、キューの外で起きている。** `main` との衝突で draft に戻した 11 件（10 本）は、どれもキューに入る前のブランチの段階で、Factory の仕組みのファイル（`scripts/factory/claim*.ts` など 4 つ）に集中していた。キューの設定（並列・scopes）では減らない。
- 試す順番は、**① `checks_timeout` を明示する → ② 不具合の直しを先に通す優先度 → （保留）並列・まとめての確かめ**。①②は今の「その場」方式（PR そのものの上で CI を回し直す。一時的な draft PR を作らない）のまま入れられる。並列・まとめての確かめは、一時的な draft PR を作る方式に変わり、PR 本文の検査と Ruleset の設定を変える必要があるので、今は勧めない。

## 案

### ① `checks_timeout` を明示する（勧める）

- **今**: 書いていないので既定の `auto`（キューの最近の CI の時間の 95 パーセンタイルに余裕を足した値）。CI が 45 秒前後なので、待ち時間は 3 分 33 秒になり、CI の実行機の順番待ちだけで外れた（#318、#328）。
- **案**: `queue_rules` の `default` に `checks_timeout: "10 minutes"` を書く。
- **効き目の見込み**: 実行機の順番待ちによる時間切れがなくなる（記録では 218 本中 1 回。混む時間帯ほど起きやすい）。
- **リスク**: CI が本当に止まったとき、キューの先頭が最大 10 分ふさがる。
- **料金**: 設定だけ。追加の機能は使わない。
- **台帳の行の案**: 「キューに入った PR 100 本あたりの `CHECKS_TIMEOUT` の回数」。前の値は 218 本中 1 回。

### ② 不具合の直しを先に通す（勧める）

- **今**: キューは入った順。`main` を壊した直しも、ほかの PR の後ろに並ぶ（#363 で、直しが同じファイルの待ちで止まった）。
- **案**: `priority_rules` で `type:fix` を `high` にする。キューは 1 つのままなので、その場方式は変わらない。
- **効き目の見込み**: 混んだときに、不具合の直しの待ちが縮む（11-12 の午後は最大 21 分待った）。ふだんは先にいる PR が平均 1 本なので、差は小さい。
- **リスク**: `type:fix` が多いと優先の意味が薄れる。付けるのは実装の役（Issue の種類から）なので、付け方は今と変わらない。
- **料金**: 文書では、機能ごとのプランの条件を確かめられなかった（下の「確かめられなかったこと」）。
- **台帳の行の案**: 「先に 2 本以上いたときの、`type:fix` とそれ以外のキューの待ちの中央値」。

### 並列（Parallel ＋ scopes）・まとめての確かめ（batch）（今は勧めない）

- **仕組み**: scopes（ファイルのパターン）で、重ならない PR を同時にテストしてマージする。batch は複数の PR をまとめて 1 回の CI で確かめ、落ちたら分けて原因を探す。
- **今は勧めない理由**:
  1. **効くのは混んだときだけ。** キューの中の CI は 45 秒で、先にいる PR は平均 1 本。縮むのは 11-12 の午後のような一時の待ちだけ。
  2. **衝突のやり直しは減らない。** 衝突はキューに入る前のブランチで起きている。
  3. **一時的な draft PR を作る方式に変わる。** `batch_size` が 2 以上、`max_parallel_checks` が 2 以上、`mode: parallel` のどれでも変わる（公式の文書）。draft PR の本文は「まとめた PR の一覧」になるので、PR 本文の検査（`pr-body-check`）を作り直す必要がある。
  4. **Ruleset の「ブランチが最新であること」を外す必要がある。** batch・並列の確かめとぶつかる（公式の文書の勧めは無効化）。品質のゲートの設定の変更なので、人の判断になる。
- **見直す目安**: キューに入ったとき先にいる PR が 3 本以上の回が、1 日の 2 割を超えたら（今は 22/218＝約 1 割）。

### そのほか（入れない・今の仕組みで足りる）

- **複数のキュー（文書だけの速いキュー など）**: 文書の PR は 258 本中 40 本で、CI も 45 秒なので、分ける効き目は小さい。どのキューの条件にも合わない PR はキューに入らない（文書）ので、条件の漏れのほうが危ない。
- **外れた PR の自動の入り直し**: PR の条件で入れる（`queue` アクション）作りなので、条件が合えば自動で戻る（文書）。時間切れは巡回が知らせる（#358 の後の `claim.ts stalled`）。足すものはない。
- **PR の更新で外れた 9 回**: キューにいる PR へ push しないことで防ぐ（Mergify の公式の Skill の注意と同じ）。手順書の決まりの話で、設定ではない。
- **merge protections（依存の PR・凍結）**: `Depends-On:` は、続けて出す Factory の仕組みの PR に使えるかもしれないが、今日の衝突は依存ではなく同じファイルの書き換えだった。凍結は障害のときに役立つ。どちらもダッシュボードでの有効化が要り、料金は確かめられなかった。必要になったら検討する。
- **Test Engine（旧 Test Insights）**: 隔離（quarantine）は使わない（AGENTS.md の「隔離はしない・人が決める」）。検出だけを使うには、テストの結果の送信（JUnit XML と Mergify の鍵）が要り、料金も確かめられなかった。ときどき落ちるテストは、PR の CI で足した・変えたテストを 20 回くり返して見つける直し（#482）で先に試す。

## 確かめられなかったこと

- **料金・プランの条件**: Mergify の公式の文書には、機能ごとのプランの条件が書かれていなかった。公式の料金ページ（mergify.com）は、この環境から読めなかった。②の優先度を含め、どの機能も「有料かもしれない」として扱い、入れる前に人が料金ページか Mergify のサポートで確かめる（課金は人の判断）。
- **個人のアカウントのリポジトリで使える範囲**: 確かめられなかった。
