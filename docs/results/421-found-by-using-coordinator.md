# [SF-D][Epic] 取りまとめる人の立場で使って見つかった困りごとを直す（#421）の結果

連続運転 D（2026-11-12、計画は #122）のうち、取りまとめる人の立場でアプリを使って見つけた困りごとを直した Epic の結果です。使う人の立場で動かす回の 2 回目です（1 回目はメンバーの立場、#411。台帳 E16）。

## 確かめたいこと

取りまとめる人の立場でアプリを使って見つけた困りごと（`docs/product.md`、#419）から作った Issue が、次の 2 つを満たすか。

- 決めていない点を質問で決めたうえで、受入条件どおりに直る。
- 使う人の立場で動かす回の 1 回目（メンバーの立場、#411）と比べて、見つかる困りごとの種類が違う。

## 見つけ方

2026-11-12 21:48 に、main（#409 のマージ後）を `npm start` で起動した。Playwright で、まず佐藤として延長を申請した。続けて田中としてログインし、次の操作を一通り使った。

- メンバー・ステータス別・期限切れの画面で、全体の進み具合を見る。
- 延長の申請を承認する。
- 担当をまとめて替えて、元に戻す。
- 削除したタスクを元に戻す。

どの操作もエラーなく動いた。そのうえで、困りごとが 1 つ見つかった。アプリには取りまとめる人という役割が無く、申請した本人のほかはだれでも延長を承認・却下できる。`docs/product.md` では、承認は取りまとめる人の役目になっている。

## 判定

| 確かめたいこと | 結果 | 判定 |
|---|---|---|
| 決めていない点を質問で決める | 割り当ての Routine が、着手の前に 2 点（取りまとめる人の決め方・だれにするか）を質問した。答えてから 1 分で着手した | 当たり |
| 受入条件どおりに直る | マージした。22:10 に同じ流れで使い直し、直ったことを確かめた（下の表） | 当たり |
| 1 回目と見つかる困りごとの種類が違う | 1 回目（メンバーの立場）は、入口・移動・入力の使いにくさだった。2 回目（取りまとめる人の立場）は、権限（だれが何をできるか）だった | 違った（2 回で、立場ごとに違う種類が見つかった） |

## 子の Issue

| Issue | 内容 | ready → 質問 → 答え → 着手 → マージ | レビュー | 使い直して確かめたこと（22:10） |
|---|---|---|---|---|
| #420 | 期限の延長を承認・却下できるのを、取りまとめる人だけにする | 21:49 → 21:50 → 21:51 → 21:51 → 22:07（18 分） | 1 回目で ok（PR #422）。risk:high。人が差分を読んだ | メンバーの鈴木: 承認待ちの一覧に承認・却下のボタンが出ず、「取りまとめる人が判断します」と出た。「あなたの対応が必要なもの」に佐藤の申請が出なかった。画面を通さずに API で承認すると 403 になった。取りまとめる人の田中: 「あなたの対応が必要なもの」に出て、承認でき、期限が延びた。申請した佐藤: これまでどおり申請できた |

答えた内容は次のとおり。

- 決め方: 利用者の表に役割の列を足し、初期データで決める。
- だれにするか: 初期の 3 人のうち、田中だけを取りまとめる人にする。

時刻はすべて UTC で、D の取りまとめ役が 60 秒ごとに取った GitHub の状態の記録と、Issue が閉じた時刻による。

## 分かったこと

- 立場を変えて使うと、違う種類の困りごとが見つかった。メンバーの立場では入口と使いにくさ、取りまとめる人の立場では権限だった。権限の抜けは、それまでのどの Issue の受入条件にも出ていなかった。どの Issue も「本人の申請は承認できない」（#333）までしか決めていなかった。
- 決めていない点は、割り当ての Routine が着手の前に質問に回した。Routine が自分で質問したのは、これで 4 件中 4 件（#316・#378・#379・#420）。
- 使い直しの前に、起動したアプリが新しいビルドかを確かめた（#411 で、古いアプリに当たって 1 回目が無効になったため）。今回はやり直さずに済んだ。

## 残したこと

- 取りまとめる人を画面から変える機能は、対象外にした。今は DB を直接変えるしかない。
- 使う人の立場で動かす回を、何件マージするごとに入れるとよいかは、まだ決めていない（台帳 E16）。
