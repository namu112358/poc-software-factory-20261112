# 結果の概要（Software Factory の PoC）

## 確かめたかったこと

GitHub のイベントで起動する Claude Code の Routine（実装・レビュー・修正・割り当て・巡回・振り返り）だけで、Issue → 実装 → PR → レビュー → 修正 → マージを、人の手をほとんど入れずに回せるかを確かめた。題材はタスク管理アプリ。2026-11-12〜13 に、A〜E の子セッションが人の役を受け持ち、次のことを見た。
- 流れとキュー（並列・衝突・待ち）
- 自己改善（振り返りと「罠」の決まり）
- 使う人の立場での困りごと
- 運用で止まる原因

## 全体の結論

- **回った。** `claude/` の PR が 220 本マージされた。そのうち、Routine の実装の PR（`claude/issue-*`）が 127 本。承認（`ready`）からマージまでの中央値は 29 分（4 分〜6 時間 16 分）。1 回目のレビューで ok は 127 本中 118 本（93%）。（2026-11-13 01:16 UTC に REST で数えた）
- **衝突による差し戻しは、直した後は無くなった。** 05:00〜08:50 は 11 本で、レビューのやり直しが 13 回あった。直した 09:00 以降は 56 本で 0 回（台帳 #123「1 本の PR の手間」）。
- **空振りの起動は、承認と開始の合図を分けて減った。** 54%（174 回中）から 17%（23 回中）になった（[165](165-improvement-effects.md)）。
- **時間を延ばしたのは、作業ではなく止まりと待ち。** 止まりも待ちも無ければ、小さな変更は 8〜18 分でマージまで進んだ。主な止まりの原因は次の 4 つ（[D-interim](D-interim-2026-11-12.md)）。
  - 使用量の上限（3 回）
  - 起動のトリガーが外れた（72 分）
  - 同じファイルの待ち
  - `main` の CI を壊した不具合
- **人の手は、流れを戻すことだけに使った。** 中身を変える人の手は 0 件（D-interim の KPI 表）。

## 原則

台帳 #123 の「原則」の節から（詳しくは台帳）。

1. 1 つのラベル（状態）には、1 つの意味だけを持たせる（`ready` が承認と開始を兼ねて、実装の起動の 54% が空振りした）。
2. 決まった判定はスクリプト（`scripts/factory/claim.ts`）に置き、手順書には判定の文を書かない。
3. 手順書は短く保つ。判定の説明はスクリプトの README に置く。
4. `AGENTS.md` には、コードを読んでも分からない決まりだけを置く。一覧や説明は `docs/` に移す。
5. 試すための Issue を量で流さず、すでにある記録で確かめる。
6. 仮説 → 直し → 測る → 次の一手、の 1 周で回す。改善の PR は、台帳に仮説と測り方の行があるものだけ出す。
7. 同じ仕事を 2 つの役が同時に始めないようにする。状態は GitHub だけに持ち、動く前と後に読み直し、開始の合図を付ける役を 1 つに絞る。数秒のすき間の重なりは残るので、重なっても害が小さい作りで受ける。
