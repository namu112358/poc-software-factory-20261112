# [SF-E][Epic] 改善の効き目（#165）の結果

台帳 #123 の課題を直した後、その直しが効いたかを確かめた結果です。いちばん大きな確かめは、実装の開始の合図を `ready` から `in-progress` に変え、着手の判断を割り当ての役にまとめた直し（PR #285）の効き目です。課題ごとの判定の正本は台帳 #123 の表で、ここにはその要約と、#285 の前後の数字を置きます。

## #285 の効き目（実装の開始の合図を分けた直し）

### 確かめたいこと

`ready` が「承認」と「実装の開始」の 2 つの意味を持っていたため、実装の Routine が起動しても、待ちに戻す・難しい用に回すなどで実装に入らない起動（空振り）が多く、1 時間あたりの起動の上限（#250）に当たっていた。開始の合図を `in-progress` に分け、着手してよいかの判定を割り当ての役（`claim.ts`）にまとめると、空振りが減り、上限に当たらなくなるか。

### 判定: 効いた

前に置いた基準は「空振りが 20% 以下」「起動の上限による止まりが起きない」「作業中 0 件のまま待つ Issue が 1 時間を超えて放置されない」の 3 つ。**3 つとも満たした**。

- 空振りは 54% → 17%。残った 4 回のうち 2 回は、実装の役が仕様の確認で止まったもの（#94 は #326 の前。#333 は、コードとの食い違いを実装中に見つけたもの）で、割り当ての時点では見つけられない種類。
- 起動の上限には当たらず、取りこぼしは 0。
- 3 つ目の基準は、待つ理由のある待ちを「放置」に数えずに判定した。#94・#259 は、`merge` を付けた PR #292 と同じファイルを変えるので待っていた（承認から最大 216 分）。待つ理由の無い待ちの最大は #350・#351 の 43 分で、1 時間は超えなかった（#357）。
- 承認から開始までの時間は、仮説どおり延びた（中央値 0.6 分 → 6.5 分）。上位 25% は「前と同じ程度」という仮説より長かった（12.9 分 → 36 分）。理由は 2 つ。
  - 同じファイルの待ち（#94・#259 は、マージ待ちの PR と同じファイルを待った）。
  - 作業中が減って PR も閉じない時間帯は、次の巡回まで割り当てが動かない（#357。#350・#351 が 43 分待った）。

### 比べるときの注意

- 16:00 に、実装・レビュー・修正の Routine を別のアカウントに移した。利用上限（#284）と GitHub のイベントの上限（#250）の数え方が前と同じではない。取りこぼしが 0 になったのが #285 のおかげか、アカウントを分けたおかげかは、この記録だけでは分けられない。
- 「後」は流した量が少ない（2 時間 15 分で 23 回。前は 10 時間半で 174 回）。

### 次の一手

- #285 の形（承認と開始を別のラベルにし、開始は判定を終えた役だけが付ける）を、標準の案に入れる。
- 承認から開始までの待ち（#357）は、次の仮説にする。たとえば、`status:ready` が付いたときにも割り当ての役を起動する。Routine の設定を変えるので、人が決める。

## 分かったこと

- **1 つのラベルに 2 つの意味を持たせない。** `ready` が「承認」と「開始」を兼ねていたことが、空振りの 54% の原因だった。分けると 17% になった。同じ形は `needs-human`（人の判断と、持ち主が直す作業）にもあり、E3（#335）で直した。
- **試すための Issue を量で流さなくても、すでにある記録で多くを判定できる。** この Epic の後半の判定は、新しい Issue を流さずに、その日のイベントとコメントから数えた。
